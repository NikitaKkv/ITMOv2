# Research: Логика и структуры данных для экспорта истории игры в JSON

**Feature**: `001-export-game-history` | **Date**: 2026-10-22

Данный документ консолидирует технологические и архитектурные решения для реализации логики экспорта истории игры в JSON в веб-приложении WordBridge.

---

## 1. Структура экспортируемого документа и версионирование схемы (Envelope Pattern)

### Решение
Использовать паттерн обёртки метаданных (`ExportEnvelope`), включающий:
- `schemaVersion`: семантическая версия формата данных (`"1.0.0"`).
- `appName`: `"WordBridge"`.
- `exportedAt`: метка времени генерации файла в формате ISO 8601 (`YYYY-MM-DDTHH:mm:ss.sssZ`).
- `summary`: сводная агрегированная статистика по сессии (`totalRounds`, `soloRoundsCount`, `duelRoundsCount`, `averageSteps`, `duelStats`).
- `rounds`: массив объектов записей завершённых раундов (`GameRoundRecord`).

### Обоснование
1. Наличие мета-обёртки и `schemaVersion` гарантирует расширяемость формата в будущем без нарушения обратной совместимости при добавлении новых игровых режимов или аналитических полей.
2. Сводка (`summary`) позволяет внешним утилитам и пользователю сразу оценить общие результаты без необходимости полного прохода по всем элементам массива.
3. Единый формат записи для соло и дуэли унифицирует парсинг, различая данные только по полю `mode` (`"solo"` | `"duel"`).

### Рассмотренные альтернативы
- **Плоский массив раундов `[{...}, {...}]`**: Отклонен, так как теряются метаданные экспорта (версия схемы, дата генерации, сводная статистика) и затрудняется будущая валидация.
- **Раздельные файлы для соло и дуэли**: Отклонен, так как пользователь ожидает единый экспорт всей игровой сессии.

## 2. Механизм сохранения файла в браузере (File Download)

### Решение
Клиентский экспорт через `Blob` и временный объектный URL:
1. Сериализация данных в JSON-строку с форматированием в 2 пробела (`JSON.stringify(envelope, null, 2)`).
2. Создание `Blob` с MIME-типом `application/json;charset=utf-8`.
3. Создание временного URL через `URL.createObjectURL(blob)`.
4. Динамическое создание элемента `<a download="wordbridge-history-YYYY-MM-DD-HHmmss.json">` и программный вызов `.click()`.
5. Немедленное освобождение ресурсов через `URL.revokeObjectURL(url)`.

### Обоснование
1. Чистый Vanilla JS без внешних зависимостей (типа FileSaver.js).
2. Полная поддержка кириллицы (UTF-8).
3. Высокая скорость работы (генерация для 100 раундов занимает единицы миллисекунд).
4. Безопасность: не требует передачи данных на сервер, всё происходит локально на устройстве пользователя.

### Рассмотренные альтернативы
- **Открытие Data URI `data:application/json;...` в новой вкладке**: Отклонен из-за ограничений браузеров по длине URL и неудобного UX (не запускает скачивание файла автоматически).
- **Серверный эндпоинт генерации файла**: Отклонен, так как архитектура проекта является полностью клиентской (Static Web App).

## 3. Копирование JSON в буфер обмена (Clipboard API)

### Решение
Использование асинхронного `navigator.clipboard.writeText(jsonString)` с обработкой ошибок и фоллбэком:
1. Проверка доступности `navigator.clipboard` и `window.isSecureContext`.
2. В случае успешной записи — временная смена текста кнопки/тултипа на «Скопировано! ✓» на 2 секунды.
3. В случае отказа в доступе (например, контекст безопасности или запрет пользователя) — автоматический вызов скачивания файла с предупреждением пользователя.

### Обоснование
- Стандартное современное API для буфера обмена.
- Высокая скорость, бесшовный пользовательский опыт для вставки в чаты или анализаторы.

### Рассмотренные альтернативы
- **`document.execCommand('copy')` через скрытый textarea**: Устаревший (deprecated) API. Оставлен только как крайний резервный вариант.

## 4. Управление состоянием истории в приложении (Session History Storage)

### Решение
1. Хранение истории завершённых раундов в оперативной памяти игрового состояния: `state.history = []`.
2. Фиксация снимка раунда происходит детерминированно в момент наступления победного условия:
   - В Solo-режиме: при вызове `finishGame()` после замыкания моста.
   - В Duel-режиме: при переходе на экран `showdown` (после завершения ходов обоих игроков) и фиксации вердикта взаимного судейства.
3. Структура раунда в истории является неизменяемым глубоким снимком (immutable snapshot) на момент завершения, что исключает мутации при старте нового раунда.

### Обоснование
- Простота и полное отсутствие побочных эффектов.
- Гарантия консистентности: незавершённые ходы текущей игры не попадают в историю экспорта.

### Рассмотренные альтернативы
- **`localStorage`**: Не требуется по текущей спецификации (Assumptions фиксируют in-memory сессию), но архитектура структуры данных полностью совместима с сохранением в `localStorage` в будущем без изменений схемы.

## 5. Стратегия тестирования и изоляция чистой логики (TDD Strategy)

### Решение
1. Выделение логики сборки структуры данных, валидации целостности, агрегации статистики и сериализации в чистые функции без привязки к DOM.
2. В соответствии с архитектурой проекта:
   - Создание тестов чистой логики на Python в `tests/test_history_export.py` (или интеграция в `tests/test_logic.py`), проверяющих:
     - Валидацию корректности структуры раунда (Solo и Duel).
     - Расчёт сводной статистики (`calculate_session_summary`).
     - Сериализацию и проверку контракта схемы JSON (RFC 8259, UTF-8, отсутствие `undefined`/`null` в обязательных полях).
     - Краевые случаи (пустая история, оспоренные ходы, спецсимволы в словах).
   - Синхронная реализация логики в JavaScript (`src/history.js` или модуль экспорта в `src/app.js`), проверяемая через `node -c` и интеграционные тесты.

### Обоснование
- Полное соответствие правилам проекта и навыку TDD (Red-Green-Refactor).
- 100% воспроизводимость проверок через существующий скрипт `scripts/check_all.sh`.

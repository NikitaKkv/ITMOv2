# Классификация Issue

## Контекст

Внутренний инструмент мейнтейнера репозитория. Фронтенд вызывает webhook n8n
(Workflow 1 из практики 7.2), который классифицирует Issue и проставляет лейбл.
GitHub-токен хранится в n8n Credentials и в клиент не передаётся.

Основной сценарий: мейнтейнер вводит репозиторий, номер Issue, заголовок и текст →
«Классифицировать» → видит тип, confidence и статус «Лейбл проставлен в #N».

## Поля и валидация

1. Repository обязателен, формат `owner/name`. Пусто или без `/` — ошибка.
2. Issue number обязателен, целое число > 0.
3. Title обязателен, 5–120 символов. Строка из пробелов не подходит.
4. Body обязателен, минимум 10 символов.
5. Ошибки показываются рядом с полем и связаны с ним через `aria-describedby`,
   у поля выставляется `aria-invalid`.

## Поведение

6. Во время запроса кнопка заблокирована, повторный клик и Enter не создают второй запрос.
7. Enter в любом поле, кроме Body, отправляет форму. В Body Enter — перенос строки.
8. При успехе показываются тип (`bug` / `task` / `feature`), confidence и «Лейбл проставлен в #N»,
   запись добавляется в таблицу «Обработанные Issue».
9. При ошибке введённые значения сохраняются, показывается сообщение и кнопка «Повторить».
10. Пустая таблица — состояние «Пока нет обработанных Issue».

## Доступность

11. У каждого поля видимая подпись `<label>`.
12. Текущий фокус виден (кольцо фокуса не убирается).
13. Сценарий проходится с клавиатуры: Tab по полям, Enter — отправка.
14. На ширине 375px содержимое читается, элементы управления доступны.

## Приёмка

После ответа 500 введённые значения остаются в полях, повторная отправка
во время ожидания не создаёт второй запрос.
